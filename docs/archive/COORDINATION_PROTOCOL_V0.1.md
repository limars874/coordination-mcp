# Coordination Protocol V0.1 Draft

**Status:** Draft  
**Version:** 0.1  
**Purpose:** Minimal shared work-state protocol for coordination between ChatGPT, local coding agents, and future participants.

---

## 1. Goal

Coordination Protocol provides a small shared state layer through which multiple AI participants can exchange durable work state without requiring the user to manually copy and paste tasks, results, findings, and other execution context.

The protocol is intentionally **not**:

- an issue tracker;
- a workflow engine;
- an autonomous agent framework;
- a chat transport;
- a filesystem;
- a general-purpose memory system;
- a notification system.

Its responsibility is limited to:

> Store durable shared work state and make that state reliably retrievable by multiple participants.

---

## 2. Core concepts

V0.1 defines four concepts:

```text
Scope
Ticket
Update
Artifact
```

Only three are stored domain objects:

```text
Ticket
Update
Artifact
```

`Scope` is a namespace used to isolate projects within one Coordination server.

---

## 3. Scope

A Scope identifies one logical coordination space.

Examples:

```text
local-files-mcp
coordination-mcp
personal-website
```

One Coordination server MAY host multiple scopes.

Scope is not a project-management object in V0.1. It has no required description, owner, mission, permissions, settings, or workflow.

### 3.1 Scope identifier

```text
scope: string
```

Scope identifiers SHOULD be stable and human-readable.

---

## 4. Ticket

A Ticket represents:

> A unit of work whose current state is worth tracking independently.

Examples:

```text
Implement search_text
Investigate MCP binding failure
Review authorization boundary
Fix CRLF line numbering
```

A Ticket represents **current mutable state**.

### 4.1 Schema

```yaml
Ticket:
  id: string
  scope: string
  title: string
  status: string
  created_by: string
  created_at: timestamp

  artifact_ids?: string[]
  meta?: object
```

### 4.2 Required fields

#### id

Globally unique opaque identifier.

IDs SHOULD be generated by the Coordination server and MUST NOT depend on scope for uniqueness.

#### scope

The Scope containing this Ticket.

#### title

Short human-readable description.

#### status

Current lifecycle state.

V0.1 defines:

```text
open
active
blocked
done
```

Clients SHOULD tolerate unknown future status values.

#### created_by

Descriptive provenance only.

Examples:

```text
user
chatgpt
local-ai
pi
codex
```

It is not an authenticated security identity.

#### created_at

Server-assigned creation timestamp.

### 4.3 Optional fields

#### artifact_ids

Artifacts directly associated with the Ticket.

Artifacts are cumulative. Removing historical artifact associations SHOULD generally be avoided.

Artifact ordering MUST NOT be treated as version semantics.

#### meta

Extension data not understood by the core protocol.

Example:

```yaml
meta:
  priority: high
  component: search
```

Core protocol behavior MUST NOT depend on unknown metadata fields.

Clients MUST tolerate unknown metadata.

V0.1 SHOULD prefer shallow scalar metadata:

```text
string
number
boolean
null
```

Agent-specific keys SHOULD use namespaced names where practical:

```yaml
meta:
  pi.last_run: "..."
  chatgpt.review_mode: strict
```

---

## 5. Ticket mutability

Tickets represent current state and are mutable.

```text
id             immutable
scope          immutable
title          mutable
status         mutable
created_by     immutable
created_at     immutable
artifact_ids   mutable / cumulative
meta           mutable
```

Changing a Ticket MUST NOT modify associated Update or Artifact objects.

---

## 6. Update

An Update represents:

> A durable statement about something that happened, was discovered, decided, or reported.

Updates form the historical timeline of Coordination state.

They are **not chat messages**.

Only information worth preserving for future participants should become an Update.

Examples:

```text
Implementation completed.
CRLF line numbering is incorrect.
Do not introduce ripgrep in V1.
This work was split into T-12 and T-13.
```

### 6.1 Schema

```yaml
Update:
  id: string
  scope: string
  seq: integer

  ticket_id?: string

  type: string
  body: string

  created_by: string
  created_at: timestamp

  artifact_ids?: string[]
  meta?: object
```

### 6.2 Fields

#### id

Globally unique opaque identifier.

#### scope

Scope containing the Update.

#### seq

Server-assigned monotonically increasing sequence number.

`seq` is monotonic **within a scope** and is used for synchronization.

It is not an object identifier.

#### ticket_id

Optional Ticket association.

When present, the Update concerns a specific Ticket.

When absent, the Update applies to the Scope as a whole.

This allows project-level decisions/findings without inventing a special Project Ticket.

#### type

V0.1 defines conventional values:

```text
note
result
finding
decision
```

Clients SHOULD tolerate additional future types.

#### body

Short durable textual content.

Long content SHOULD be stored as an Artifact.

#### created_by

Descriptive provenance label, not a security identity.

#### created_at

Server-assigned timestamp.

#### artifact_ids

Optional immutable references to supporting Artifacts.

#### meta

Optional extension data under the same rules as Ticket metadata.

---

## 7. Update immutability

Updates are append-only.

After creation, every Update field is immutable.

There is no:

```text
edit_update
update_update
delete_update
```

If an Update contains incorrect information, create another Update.

V0.1 does not define revision or supersedes semantics.

---

## 8. Artifact

An Artifact represents:

> Immutable shared textual content that all Coordination participants can retrieve through the Coordination service.

Artifact exists primarily to solve cross-environment accessibility.

Local filesystem paths alone are insufficient because different agents may not have access to the same filesystem.

Coordination therefore owns the minimal shared Artifact store.

### 8.1 Schema

```yaml
Artifact:
  id: string
  scope: string

  media_type: string
  content: string

  created_by: string
  created_at: timestamp

  meta?: object
```

### 8.2 Semantics

Artifacts are:

```text
globally uniquely identified
immutable
append-only
text-oriented
flat in identity/storage semantics
not deleted in V0.1
```

Typical media types:

```text
text/plain
text/markdown
application/json
```

Binary Artifact support is outside V0.1.

### 8.3 Immutability

Once created, Artifact content, media type, and scope cannot change.

If content changes, create a new Artifact.

No built-in version chain is required.

Historical references remain stable forever.

### 8.4 Storage model

Artifact identity is globally flat.

Logical relationship:

```text
Ticket T-10
  -> Artifact A-100

Update U-20
  -> Artifact A-101
```

Physical implementation SHOULD NOT require hierarchical identity such as:

```text
T-10/U-20/A-101
```

Lookup uses only Artifact ID:

```text
get_artifact(A-101)
```

Artifacts do not require backlinks.

Relationships are stored by the referring Ticket or Update.

### 8.5 Deletion

V0.1 provides no Artifact deletion operation.

Deletion or garbage collection should only be considered after real scale makes storage significant.

---

## 9. Relationship philosophy

V0.1 intentionally has no generic relationship graph.

It does not define:

```text
parent
child
depends_on
blocks
duplicates
supersedes
related_to
fixes
```

Relationships SHOULD initially be expressed through Updates.

Example:

```text
Work split into T-21 and T-22.
```

Metadata MAY temporarily carry machine-readable relationship hints.

A formal relationship model should only be introduced after multiple real use cases require it.

---

## 10. Long content rule

Core protocol objects should remain small.

```text
Ticket -> current coordination metadata
Update   -> short durable statement
Artifact -> long content
```

Examples suitable for Artifact:

```text
implementation spec
execution report
architecture proposal
security review
handoff
investigation report
large structured output
```

An **Implementation Spec** is simply one common kind of Artifact content. It is not a protocol primitive.

The Coordination protocol does not interpret the internal schema of those documents.

---

## 11. Synchronization model

Coordination is a durable state store, not a message queue.

Each Scope maintains a monotonically increasing Update sequence.

An Agent MAY maintain:

```text
cursor[scope] = last_seen_seq
```

To synchronize:

```text
list_updates(scope, after_seq)
```

Results MUST be ordered by ascending `seq`.

`after_seq` is exclusive.

### 11.1 Cursor semantics

A cursor means:

> Updates successfully retrieved by this participant up to this sequence.

It does NOT mean task completed, Update fully processed, work accepted, or result reviewed.

Coordination V0.1 does not implement reliable queue acknowledgements.

---

## 12. Notification / Wake-up layer

Notification is deliberately separate from durable Coordination state.

Wake-up behavior is agent-runtime-specific.

V0.1 defines only a conceptual contract and does not implement adapters.

### 12.1 Wake-up contract

A Wake-up signal contains:

```yaml
scope: local-files-mcp
latest_seq: 103
```

Semantics:

> Coordination state in this Scope may have changed. Resynchronize from your own cursor.

The notification does not deliver the authoritative Update.

After receiving the signal, the participant should perform:

```text
list_updates(scope, after_seq=local_cursor)
```

`latest_seq` is only a hint.

### 12.2 Reliability

Wake-up delivery is best-effort.

Signals MAY be lost, duplicated, delayed, or coalesced.

Correctness MUST NOT depend on notification delivery.

> Wake-up is a hint to resync, not a delivery mechanism.

---

## 13. MCP interface — V0.1

Proposed core operations:

```text
list_tickets
get_ticket
create_ticket
update_ticket

list_updates
add_update

create_artifact
get_artifact
```

No generic `do_anything(action, payload)` endpoint should be introduced.

---

## 14. create_ticket

Input:

```yaml
scope: string
title: string

status?: string
created_by: string

artifact_ids?: string[]
meta?: object
```

Default:

```text
status = open
```

Server assigns:

```text
id
created_at
```

Output:

```yaml
ticket: Ticket
```

---

## 15. get_ticket

Input:

```yaml
id: string
```

Output:

```yaml
ticket: Ticket
```

Because Ticket IDs are globally unique, scope is not required for direct lookup.

---

## 16. list_tickets

Input:

```yaml
scope: string

status?: string
limit?: integer
cursor?: string
```

Output:

```yaml
items:
  - Ticket
  - Ticket

next_cursor?: string
```

`cursor` here is pagination state and is distinct from Update `seq`.

V0.1 SHOULD keep filtering minimal.

---

## 17. update_ticket

Updates mutable Ticket fields.

Input:

```yaml
id: string

title?: string
status?: string
artifact_ids?: string[]
meta?: object
```

Output:

```yaml
ticket: Ticket
```

Immutable fields cannot be changed.

Server MUST reject attempts to modify:

```text
id
scope
created_by
created_at
```

V0.1 does not require optimistic concurrency control.

Simple serialized mutation / last-write-wins behavior is acceptable.

For `artifact_ids`, implementations SHOULD prefer append semantics or otherwise avoid lost updates when multiple participants add artifacts concurrently.

---

## 18. add_update

Creates an immutable Update.

Input:

```yaml
scope: string

ticket_id?: string

type: string
body: string

created_by: string

artifact_ids?: string[]
meta?: object
```

Server assigns:

```text
id
seq
created_at
```

If `ticket_id` is present, the referenced Ticket MUST exist and belong to the same scope.

Output:

```yaml
update: Update
```

---

## 19. list_updates

Primary synchronization API.

Input:

```yaml
scope: string

after_seq?: integer
ticket_id?: string
type?: string

limit?: integer
```

Output:

```yaml
updates:
  - Update
  - Update

latest_seq: integer
has_more: boolean
```

Results MUST be ordered by ascending `seq`.

`after_seq` is exclusive.

Filtering by `ticket_id` or `type` is optional convenience.

Synchronization correctness should rely on unfiltered scope-level sequence retrieval.

---

## 20. create_artifact

Creates immutable shared textual content.

Input:

```yaml
scope: string
media_type: string
content: string
created_by: string
meta?: object
```

Server assigns:

```text
id
created_at
```

Output:

```yaml
artifact:
  id: string
  scope: string
  media_type: string
  created_by: string
  created_at: timestamp
  meta?: object
```

The server MAY omit `content` from the create response when content is large.

---

## 21. get_artifact

Input:

```yaml
id: string
```

Output:

```yaml
artifact: Artifact
```

Direct lookup does not require scope because IDs are globally unique.

---

## 22. Referential integrity

When creating or updating an object with `artifact_ids`, each referenced Artifact MUST:

1. exist;
2. belong to the same Scope.

Cross-Scope references are not supported in V0.1.

When creating an Update with `ticket_id`, the Ticket MUST belong to the same Scope.

---

## 23. ID semantics

IDs are opaque.

Clients MUST NOT infer creation time, scope, storage path, object hierarchy, or agent identity from an ID.

Prefixes such as:

```text
T-
U-
A-
```

are recommended for human readability but are not semantically required.

---

## 24. Ordering

Update ordering is authoritative through `seq`.

`created_at` is informational and MUST NOT be used as the primary synchronization ordering mechanism.

Ticket and Artifact creation ordering does not require sequence numbers in V0.1.

---

## 25. Error model

Recommended stable error categories:

```text
NOT_FOUND
INVALID_ARGUMENT
INVALID_REFERENCE
SCOPE_MISMATCH
IMMUTABLE_FIELD
UNSUPPORTED_MEDIA_TYPE
CONFLICT
INTERNAL_ERROR
```

Errors SHOULD include a human-readable message.

Clients SHOULD NOT depend on exact error message text.

---

## 26. Agent identity

Coordination V0.1 does not define agent authentication or capability negotiation.

`created_by` is provenance only.

Security identity, transport authentication, MCP authorization, and access control are implementation concerns outside this protocol draft.

---

## 27. User control

Coordination does not imply autonomous execution.

Typical workflow remains:

```text
ChatGPT creates proposed Ticket / Artifact
        ↓
User decides to proceed
        ↓
Local AI executes
        ↓
Local AI adds Result Update
        ↓
User asks ChatGPT to review
        ↓
ChatGPT adds Finding / Decision
```

Reducing manual data transport does not require removing human approval.

---

## 29. Example — implementation flow

ChatGPT creates implementation spec:

```text
create_artifact
→ A-100
```

Then:

```text
create_ticket
→ T-20
→ artifact_ids=[A-100]
```

Local AI synchronizes and reads:

```text
get_ticket(T-20)
get_artifact(A-100)
```

After implementation:

```text
create_artifact
→ A-101 execution report
```

Then:

```text
add_update
  ticket_id=T-20
  type=result
  artifact_ids=[A-101]
```

ChatGPT reviews and discovers a defect:

```text
add_update
  ticket_id=T-20
  type=finding
  body="CRLF line numbers are incorrect."
```

Then Ticket:

```text
status:
done → active
```

No chat transcript is required in Coordination.

---

## 30. Design rules

1. **Ticket is current state.**
2. **Update is immutable history.**
3. **Artifact is immutable shared content.**
4. **Scope isolates projects.**
5. **seq provides reliable incremental synchronization.**
6. **Notification is optional and non-authoritative.**
7. **Long content belongs in Artifacts.**
8. **Unknown metadata must not change core semantics.**
9. **Relationships should remain textual until proven necessary.**
10. **New abstractions require multiple real use cases.**

---

## 31. Short definition

> Coordination Protocol is a tiny shared work-state protocol built around mutable Tickets, immutable Updates, and immutable shared Artifacts, organized by Scope and synchronized through monotonic Update sequences.

---

## 32. V0.1 stability boundary

Candidates for freezing during initial implementation:

```text
Scope namespace
Ticket
Update
Artifact
immutable Update
immutable Artifact
scope-local Update seq
optional ticket_id
optional meta
artifact_ids
best-effort Wake-up Contract
```

Everything else should remain open to change until the protocol has been exercised against real workflows.

The next validation step should be implementation and testing against real ChatGPT ↔ User ↔ Local AI workflows rather than further speculative expansion.
